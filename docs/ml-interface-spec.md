# WearCare Mate - AI/ML 인터페이스 스펙 (v0.5)

- 작성: 조채환 (AI/ML 파트) / 2026-10-30
- 상태: **초안 - 팀 확인 필요** (확인 요청은 10번)
- 범위: 이상 탐지와 Bedrock 가이드 생성의 입력/출력 약속
- v0.2 대비 변경: 집단 기준 규칙 확정 (5번), SLEEP_QUALITY_LOW를 SLEEP_RESTLESS로 교체, 수면 점수 지표 제외

## 1. 한 줄 요약

하루 단위 웨어러블 지표를 받아 이상 징후를 찾고, 이상이 있으면 그 결과로 **맞춤형 행동 가이드(3줄)**를 돌려준다. 이상은 두 방식으로 찾는다: 사용자 본인의 평소 기록과 비교(개인 기준선), 전체 데이터 분포와 비교(집단 기준).

## 2. 데이터 현황 (2026-10-30 직접 확인한 내용)

| 데이터 | 확인 결과 | 사용 방식 |
|---|---|---|
| Fitbit 활동 (`fitbit_activity_table`) | 사용자 35명 (실제 Id), 2016-03-12~04-12, 사용자당 기록 중앙값 12일 (최소 8, 최대 32). 14일 이상 8명, 21일 이상 2명 | **개인 기준선** (활동량) |
| 수면 (`wearable_sleep_table_fixed`) | 1,000행, `Sleep_Quality_Score`는 약 70%(69.7%)가 1.0이라 **사용 불가**, UserId가 모두 `user_test`, RecordTime이 1분 간격으로 부여된 값. 행마다 값이 독립적이라 **사용자별 연속 기록이 아님** | **집단 기준** (수면, HRV, 스트레스) |
| 안정시 심박 | 두 테이블 모두 없음 | 보류 (PMData 적재 또는 Fitbit 심박 파일 필요) |

주의할 점
- **Fitbit 날짜 오류**: 457행 중 385행의 `ActivityDate`가 깨져 있다 (예: `2004-01-16` = 실제 `2016-04-01`, `2003-12-16` = 실제 `2016-03-12`). 변환 규칙으로 보정했고 보정 후 기간과 중복은 정상이었다. **원본에서 다시 적재 필요** (10번).
- **마지막 날(2016-04-12)은 불완전한 하루**로 보인다 (걸음 수 중앙값 1,019 vs 평소 7,352). 판정에서 제외한다.
- 걸음 수 0인 61행은 기기 미착용으로 보고 제외한다 (가정, 확인 필요).
- 수면 테이블의 UserId와 RecordTime은 임의로 부여된 값이다. 발표에서 합성/임의값임을 밝힌다.
- 수면 테이블과 Fitbit 테이블은 **서로 다른 데이터셋**이라 같은 사용자로 묶을 수 없다.

## 3. 탐지 방식

| | A. 개인 기준선 | B. 집단 기준 |
|---|---|---|
| 대상 | 활동량 (걸음 수) | 수면 시간, HRV, 스트레스, 수면 중 움직임 |
| 비교 대상 | 해당 사용자의 직전 기록 | 데이터 전체 분포 |
| 이상 유형 | ACTIVITY_DROP | SLEEP_SHORT, HRV_LOW, STRESS_HIGH, SLEEP_RESTLESS |
| 구현 | 이동 기준선 z-score (파이썬, Lambda 호환) | SageMaker 이상 탐지 (Isolation Forest 또는 Random Cut Forest) + 지표별 집단 대비 편차로 이유 설명 |
| 상태 | **v0.1 로직 구현 및 주입 테스트 완료** | **기준값 확정, 로직 확인 완료 (v0.3)**. SageMaker 노트북 이식 전 |

**RHR_HIGH(안정시 심박 상승)는 보류.** 데이터가 없다. PMData가 적재되면 A 방식으로 추가한다.

## 4. 개인 기준선 규칙 (ACTIVITY_DROP)

- 기준선: 해당 사용자의 **직전 기록 최대 14개** (당일 제외). 유효 기록이 **5개 미만이면 판정하지 않음** (`insufficient_data`).
- 표준편차 하한: 500보.
- 나쁜 방향(걸음 수 감소)만 이상으로 본다.
- **판정은 하루가 끝난 뒤(다음날 아침) 확정된 데이터로 한다.** 당일 진행 중인 값으로 판정하면 오탐이 난다.
- PMData처럼 기록이 길면 기준선 14일 / 최소 7일로 되돌린다.

**심각도 (z는 기준선 대비 표준화 점수, 하락률은 기준선 평균 대비)**

| 심각도 | 조건 | 쓰임 |
|---|---|---|
| low | z ≤ -1.0 이고 하락률 40% 이상 | 대시보드 표시만 |
| medium | z ≤ -1.5 이고 하락률 40% 이상 | **SNS 알림 기준** |
| high | z ≤ -2.0 이고 하락률 50% 이상 | 강한 이상 |

**주입 테스트 결과** (정답 라벨이 없어, 기준선 평균의 50%/30%로 줄인 값을 만들어 탐지율을 본 것. 마지막 날과 0걸음 제외, 사용자-날짜 215건, 사용자 31명)

| z 기준 | 실제 데이터 판정 비율 | 평소의 50%로 감소 시 탐지 | 평소의 30%로 감소 시 탐지 |
|---|---|---|---|
| 1.0 | 약 15% | 60% | 85% |
| 1.5 | 약 6.5% | 42% | 57% |
| 2.0 | 약 2% | 23% | 44% |

한계: 기준선이 5~14개 기록뿐이고 사람마다 변동이 커서 보수적으로 탐지된다. 라벨이 없어 실제 정확도는 알 수 없다.

## 5. 집단 기준 규칙 (SLEEP / HRV / STRESS) - 미정

- 입력 지표: Heart_Rate_Variability, Sleep_Duration_Hours, Stress_Level, Movement_During_Sleep
- `Sleep_Quality_Score`는 값이 1.0에 몰려 있어 쓰지 않는다. `Movement_During_Sleep`의 음수 21건(2.1%)은 0으로 보정한다.
- **나쁜 방향만** 이상으로 본다: HRV 낮음(HRV_LOW), 수면 짧음(SLEEP_SHORT), 스트레스 높음(STRESS_HIGH), 움직임 많음(SLEEP_RESTLESS). 좋은 방향의 극단값(예: HRV 매우 높음)은 이상이 아니다.
- 지표별 나쁜 방향 편차 z를 계산하고 `z = 0` 미만(좋은 쪽)은 0으로 처리한다.
- 집단 기준값(`population_stats.json`, Lambda에 함께 배포):

| 지표 | 평균 | 표준편차 |
|---|---|---|
| Heart_Rate_Variability | 70.39 | 19.58 |
| Sleep_Duration_Hours | 7.47 | 1.54 |
| Stress_Level | 4.94 | 2.03 |
| Movement_During_Sleep | 2.01 | 0.97 |

**심각도 (나쁜 방향 z 중 가장 큰 값 기준)**

| 심각도 | 조건 | 1,000건 중 실제 비율 | 쓰임 |
|---|---|---|---|
| low | z ≥ 2.0 | 7.5% (75건) | 대시보드 표시만 |
| medium | z ≥ 2.5 | 1.1% (11건) | **SNS 알림 기준** |
| high | z ≥ 3.0 | 0.5% (5건) | 강한 이상 |

- **overall_severity 실측 (`detector.py`, 수면 CSV 1,000행)**: none 909 / low 74 / medium 11 / high 6. 서로 다른 지표 2개 이상이면 한 단계 올리는 규칙은 3행에만 적용됐다. **SNS 알림 대상(medium 이상)은 17건, 1.7%.** SageMaker 노트북(ml.t3.medium, 서울 리전)에서도 같은 결과를 확인했다.
- 수면 CSV 원본 파일로 평균, 표준편차, 심각도 분포(909/74/11/6)를 직접 재계산해 위 값과 일치함을 확인했다 (2026-10-30). `RecordTime`은 2026-10-01 00:01~16:40로 1분 간격 인위 부여값.
- 처음 제안한 z 1.5 기준은 한 지표라도 걸리는 행이 24.8%여서 알림용으로 너무 느슨해 제외했다.
- `anomaly_score`: 나쁜 방향 편차 4개를 입력으로 한 Isolation Forest(200 트리, contamination 0.05)의 점수. 상위 10건은 여러 지표가 동시에 나쁜 조합이었다.
- **한계**: 점수 상위 50건 중 14건은 z 기준 심각도가 none이다 (각 지표는 약하지만 여러 개가 함께 나쁜 경우). 이런 복합 악화를 별도 단계로 올릴지는 **미검증**이라 v0.3에서는 점수를 참고값으로만 출력하고 심각도에는 반영하지 않는다.
- 데이터가 임의로 생성된 값으로 보여 **분포 기준일 뿐 의학적 기준이 아니다.**
- 카페인, 취침 일관성, 빛 노출은 탐지에 쓰지 않고 가이드의 **참고 정보**(`context`)로만 전달한다.

## 6. 입력 (백엔드 Lambda -> AI/ML)

하루에 사용자 1명, 1건. 날짜는 KST 기준, 수면은 기상한 날에 귀속한다.

```json
{
  "user_id": "1503960366",
  "date": "2016-04-10",
  "metrics": {
    "steps": 2100,
    "sleep_hours": 4.8,
    "movement_during_sleep": 2.4,
    "heart_rate_variability": 62.0,
    "stress_level": 7.1,
    "tracked_minutes": 1440
  },
  "context": {
    "caffeine_intake_mg": 240
  },
  "notify": true
}
```

- 있는 지표만 판정한다. 필수 지표가 모두 없으면 `insufficient_data`.
- `notify`(선택, 기본 `true`): `false`면 조건을 만족해도 **SNS 알림을 보내지 않는다**. 가이드 재조회, 요청 재시도, 테스트에 쓴다. 탐지 결과와 가이드는 그대로 돌려준다.
- `tracked_minutes`(선택): 그날 기록 시간 합계(활동 3종 + 비활동 분). **800분 미만이면 부분 수집으로 보고 걸음 수 판정을 건너뛴다** (11번 참고). 보내지 않으면 지금까지와 동일하게 동작한다.
- 컬럼명 별칭: `sleep_duration_hours` → `sleep_hours`, `totalsteps`/`total_steps` → `steps`. 테이블 컬럼명을 그대로 보내도 된다.
- 개인 기준선(걸음 수)용 과거 기록은 **AI/ML이 Athena에서 읽는다**: 기준일 파라미터로 `기준일 - 14일 <= 날짜 < 기준일` 조회 (오늘 기준 `CURRENT_DATE`는 과거 데이터에서 0건이라 쓰지 않음). 수면 테이블의 날짜는 문자열이라 변환이 필요하다.
- 컬럼명과 단위는 데이터 파트의 `daily_summary` 뷰와 맞춘다 (10번).

## 7. 출력 (AI/ML -> 백엔드 Lambda)

```json
{
  "user_id": "1503960366",
  "date": "2016-04-10",
  "status": "anomaly",
  "overall_severity": "medium",
  "anomalies": [
    {
      "type": "ACTIVITY_DROP",
      "basis": "personal",
      "metric": "steps",
      "value": 2100,
      "baseline_mean": 11883,
      "baseline_std": 1484,
      "z_score": -6.6,
      "drop_pct": -82.3,
      "severity": "high"
    },
    {
      "type": "STRESS_HIGH",
      "basis": "population",
      "metric": "stress_level",
      "value": 7.1,
      "population_mean": 5.0,
      "z_score": 1.9,
      "severity": "low"
    }
  ],
  "anomaly_score": 0.71,
  "guide": {
    "text": "(Bedrock이 생성한 3줄 가이드. 줄 사이는 \n)",
    "lines": ["(1줄: 이상 징후 요약)", "(2줄: 권장 행동)", "(3줄: 전문가 상담 안내)"],
    "model_id": "(사용한 모델 ID)",
    "warnings": [],
    "generated_at": "2016-04-11T08:00:00+09:00"
  },
  "alert_sent": true,
  "alert_reason": "sent",
  "model_version": "activity-zscore-v0.2+pop-v0.3"
}
```

| 필드 | 값/설명 |
|---|---|
| status | `normal` / `anomaly` / `insufficient_data` |
| overall_severity | `none` / `low` / `medium` / `high` (이상 중 가장 높은 단계. 서로 다른 지표가 둘 이상이면 한 단계 올림, high는 유지) |
| anomalies[].basis | `personal` (본인 기록 대비) / `population` (전체 분포 대비) |
| anomaly_score | 집단 기준 모델의 종합 점수 (0~1). 개인 기준만 쓰면 `null` |
| guide | status가 anomaly일 때만 생성. 그 외 `null` |
| guide.lines | 가이드 3줄의 배열. **화면에는 이 값을 한 줄씩 그리면 된다** (`text`는 같은 내용을 `\n`으로 이은 것) |
| guide.warnings | 생성 규칙 위반 경고 목록. 비어 있으면 규칙을 모두 지킨 것. 값이 있어도 가이드는 그대로 표시하면 된다 |
| alert_sent | SNS 알림을 보냈으면 `true` (아래 규칙 참고) |
| alert_reason | 발송/미발송 사유. `sent` / `disabled`(주제 미설정) / `notify_false`(요청이 `notify: false`) / `below_threshold`(medium 미만) / `duplicate`(같은 사용자+날짜 재발송 방지) / `failed`(발송 실패) |

- **SNS 알림**: `overall_severity`가 `medium` 이상일 때만. `low`는 대시보드에만 표시.
  - AI/ML Lambda(`wearcare-mate-ml`, 서울)에서 직접 발송한다. 주제: `wearcare-mate-alert`
  - 발송 여부는 응답의 `alert_sent`, 사유는 `alert_reason`으로 알 수 있다. 발송에 실패해도 탐지 결과는 그대로 돌려준다 (`alert_sent: false`).
  - **중복 발송 방지**: 같은 `user_id` + `date` 조합은 `ALERT_DEDUPE_SECONDS`(기본 6시간) 안에 다시 보내지 않는다 (`alert_reason: duplicate`). 다만 이 기록은 Lambda 실행 환경 안에만 남아서, 환경이 새로 뜨거나 동시에 여러 개가 뜨면 다시 보낼 수 있다. **확실하게 막으려면 재조회·재시도 요청에 `notify: false`를 보낸다.**
  - **테스트 중 발송 끄기**: 요청에 `notify: false`를 넣는 방법(권장, 코드 변경 없음), 환경 변수 `SNS_TOPIC_ARN`을 비우는 방법, 테스트용 주제 ARN을 넣는 방법 중 하나를 쓴다.
- 오류: `{"error": {"code": "INVALID_INPUT", "message": "..."}}` (code 예: INVALID_INPUT, MODEL_ERROR, GUIDE_FAILED). 가이드 생성이 실패해도 탐지 결과는 돌려준다 (`guide: null`).

## 8. Bedrock 가이드 규칙

- 입력: 출력의 `anomalies` 배열과 `context`.
- 한국어, 친근하고 간결한 말투, **정확히 3줄**.
- 의학적 진단, 병명, 약 처방은 하지 않는다. 일상에서 할 수 있는 행동만 제안한다.
- 입력에 없는 사실(시점, 원인, 생활 습관)을 추측하지 않는다.
- `anomalies` 배열은 **심각도 높은 순으로 정렬**해서 넘기고, 입력된 이상 징후를 빠짐없이 **입력 순서대로** 다룬다. 이모지는 쓰지 않는다.
- 수치는 입력값을 그대로 인용하고 새로 계산하지 않는다. 원인이나 지표 간 연관을 추측하지 않는다. 구체적인 행동을 1개 이상 제안한다.
- 출력은 줄바꿈으로 구분한 3줄이 목표다. 모델이 줄바꿈 없이 한 문단으로 내거나(Haiku 4.5에서 확인) 빈 줄이 섞일 수 있어, 백엔드는 **빈 줄을 제거하고, 줄바꿈이 없으면 문장 단위로 3개로 나눠** `guide.lines` 배열로 만든다.
- 말투는 해요체로 고정한다 (격식체 금지).
- 줄 구성: 1줄 이상 요약(입력 순서대로), 2줄 구체적 행동(한 문장, 수치 포함), 3줄 상담 권유 (v6, 확정). 시점은 "오늘"만, "절반" 같은 직접 계산 표현은 금지.
- **출력 검사**: AI/ML 함수가 줄 수, 문장 수, 금지어, 이모지, 상담 문구, 오늘 수치 포함 여부를 검사하고 위반이면 1회 재시도한다. 그래도 위반이면 `guide.warnings`에 사유를 담아 반환한다 (프론트는 warnings가 있어도 표시는 가능, 로그로만 수집). 입력의 "평소"(개인)와 "평균"(집단) 표현을 섞지 않는다.
- 마지막 줄은 증상이 지속되거나 불편하면 전문가와 상담하라는 문장으로 한다.
- `basis`가 `population`인 이상은 "평균 대비" 표현을 쓰고, `personal`은 "평소 대비" 표현을 쓴다.
- 모델: Claude Haiku 4.5, 호출 ID `global.anthropic.claude-haiku-4-5-20251001-v1:0` (서울 리전에서 SageMaker 노트북 역할로 boto3 converse 호출 확인, 2026-10-30). 서울에서는 직접 모델 ID나 `apac.` 접두사 ID는 안 되고 `global.` 추론 프로파일을 쓴다. 호출 역할에 `bedrock:InvokeModel`(Haiku 4.5 foundation-model과 inference-profile) 필요.
- 리전: Bedrock Playground와 SageMaker 노트북은 서울(ap-northeast-2), S3/Glue/Athena 데이터는 us-east-2(오하이오)에서 확인함. 서울 이전은 하지 않으며, 코드에서 서비스별 리전을 따로 지정한다 (Athena 조회는 us-east-2, Bedrock 호출은 서울). 모델은 품질, 비용, 지연을 비교한 뒤 확정한다 (Playground 테스트에서 응답 약 2~3초).

## 11. 데이터 주의사항 (2026-11-03 확인)

- `fitbit_activity_table`의 마지막 날 **`2016-04-12`는 부분 수집**이다. 그날 24명 평균이 1,762걸음(전체 평균 6,547걸음), 0걸음 5명, 24명 중 23명이 본인 평소의 60% 미만이다.
- 이 날짜로 탐지를 돌리면 24명 중 22명이 이상으로 잡힌다 (high 12 / medium 4 / low 6). 하루 전 `2016-04-11`은 25명 중 5명으로 정상 범위다.
- 근거를 하나 더 보면, 하루 기록 시간(활동 3종 + 비활동 분)이 평소에는 중앙값 1,440분인데 `2016-04-12`는 중앙값 426분이다. 사용자 `1503960366`의 그날 기록은 걸음 224, 기록 시간 41분이다.
- **방어 장치**: 입력 `metrics.tracked_minutes`(선택)를 주면, 그 값이 **800분 미만일 때 걸음 수 판정을 하지 않는다** (`ACTIVITY_DROP`만 `insufficient_data`, 다른 지표는 그대로 판정). 기준 800분이면 평소일은 2.8%만 제외되고 `2016-04-12`는 24명 중 21명이 걸러진다. 이 필드를 보내지 않으면 기존과 똑같이 동작한다.
- **데모와 통합 테스트의 기준일은 `2016-04-11` 이전으로 잡는다.**
